# 工程行为约束

每次 Java 实现、修改或评审都必须阅读本文件。目标是控制 Agent 的判断和改动范围，而不是补充通用 Java 知识。

## 实现前分析

先理解业务上下文，不要看到需求立即生成代码。对新增功能或涉及多个文件的修改，至少确认：

1. 当前业务流程、状态变化和数据流向。
2. 涉及模块、已有实现和可复用公共能力。
3. 输入模型、输出模型、调用方和兼容性要求。
4. 数据库、权限、事务和异常场景的影响。
5. 预计修改的文件范围，以及是否需要迁移或回填数据。

复杂任务在编码前输出简短设计：方案、修改点、风险、数据迁移结论。基于已读代码自行校验方向；只有方向存在实质分歧或需要额外授权时才向用户追问。

阅读范围从当前 Controller、对应 Service、Mapper/Entity/VO/BO、直接调用方和相邻实现开始。只有发现公共能力、共享模型或跨模块影响时才扩大范围；禁止为了理解单一需求遍历整个仓库、根据类名猜业务或因历史问题扩大修改范围。

遇到字段、接口、权限、表结构或调用链不确定时，优先搜索仓库和相邻实现；禁止假设字段已存在或创建需求未要求的接口。不得仅因代码实现方便自行新增数据库字段，也不得猜测字段名、类型、默认值或空值语义。只有代码与配置均无法确认的信息才向用户询问。

## 修改范围控制

遵循小范围修改优先原则：

- 只改实现当前需求和直接修复其阻塞问题所需的文件与代码。
- 禁止无关重构、全模块格式化、顺手修历史代码、升级依赖、替换技术方案或改变公共接口语义。
- 历史问题若直接影响当前需求，可以连同修复；否则在交付说明中记录，不主动修改。
- 不要为了“更优雅”扩大变更范围。确需扩大时，明确说明原因、影响和替代方案。
- 不得为了简单问题新增 Maven 依赖、替换既有工具类或引入重复功能库。确需新增依赖时，说明必要性、现有替代方案、安全风险和维护成本。

## 高风险操作

未经用户本次明确授权，不执行删除数据库表/字段、修改生产数据、无 `WHERE` 的 `UPDATE`/`DELETE`、修改公共组件或权限模型、大范围重构、基础框架升级或 Maven 依赖版本升级。即使需求涉及这些操作，也先确认目标、影响和回滚路径。

## 反过度设计

决策顺序固定为：**复用已有实现 > 简单扩展 > 新增抽象**。

- 简单 CRUD 不新增 Factory、Strategy、DomainEvent、Repository、Adapter、空接口或预留扩展点。
- 新增层、模式、接口或公共组件必须同时满足：已有同类约定或明确业务复杂度、至少两个真实调用点或稳定边界、能降低而非转移复杂度。
- 单次使用的辅助逻辑优先命名清晰的私有方法；不要创建 `CommonUtils`、`CommonService`、`Utils2` 等万能类。

## 反假设性代码

禁止为不存在的场景增加字段、分支、客户端兼容、默认 fallback 或“以后可能用到”的代码。仅在已上线历史数据、已发布客户端或明确迁移阶段需要兼容时允许保留，并用注释说明兼容对象、原因和移除条件。

## 重复、枚举与注释

- 相同权限判断、字段转换、查询条件或异常处理出现第三次时，评估抽取为具备业务含义的方法或组件；不要为了减少两行代码过早抽象。
- 状态、类型、分类、权限类型和操作类型不得使用无语义魔法值。优先复用项目枚举或常量，并确保数据库值与业务语义一致。
- 注释只解释业务原因、性能取舍、第三方限制、兼容策略或容易误解的规则；不要解释显而易见的赋值和流程。

## 生成前自检

在生成或提交代码前逐项确认：是否已复用能力、是否新增了不必要文件、是否扩大范围、Service 是否过重、是否有重复或魔法值、是否有性能风险、是否需要测试、是否影响数据库或权限。发现问题时先调整设计，再继续实现。

## 交付说明

完成修改后必须说明：修改文件及目的、是否涉及数据库迁移、是否影响接口契约、是否影响权限、实际执行的测试，以及未验证的风险。禁止只回复“已完成”或“代码已修改”。
