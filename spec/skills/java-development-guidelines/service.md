# Service 实现规范

Service 负责一个明确用例的编排、业务校验、事务边界和协作调用；它不是 DTO 转换、JSON/Excel 处理、展示字符串拼接或万能工具的容器。

## 复杂度与职责

- 新增或修改的 Service 公有方法原则上不超过 80 行逻辑代码；超过 100 行时，按业务步骤、事务边界、转换/计算职责和外部副作用审查是否存在独立责任。
- 存在独立责任时必须拆成命名清晰的私有方法或协作类；不得为了凑行数创建只包一层、无业务边界的类或方法。无可分离职责但保留较长直线流程时，在设计或交付说明中记录原因。
- 若本次新增或修改使 Service 明显膨胀、超过约 500 行或引入多个不相干业务域，按同一职责标准评估边界拆分。既有超长 Service 除非直接影响当前需求，否则只记录风险，不主动拆分。
- 复杂业务计算提取到 `XxxCalculator`，复杂模型组装提取到 `XxxAssembler` 或 `XxxConverter`。简单一行逻辑无需为了形式创建新文件。
- 不用 JSON 往返、反射拷贝、`Map<String, Object>` 或原始类型集合逃避类型建模。

## 集合与数据访问

- 简单无副作用转换可以使用 Stream；存在状态变更、异常分支、嵌套逻辑或超过三层 lambda 时，用普通 `for` 循环或继续拆方法。
- 禁止在循环中逐条查询导致 N+1。先批量查出数据，以 `Map`/`Set` 组装；大数据量时分页、分批或把安全聚合下推到数据库。
- 禁止在 Service 中堆叠长链式 MyBatis-Plus Wrapper。简单单表条件可以使用；复杂、多表、动态或统计查询转入 Mapper XML，详见 [mybatis.md](mybatis.md)。

## 外部调用与副作用

- 外部调用必须设置连接和读取超时，并区分连接失败、超时、非 2xx、反序列化失败和对方业务错误。
- 调用第三方或 `fund-quant` 时，明确连接/读取超时、重试次数、幂等策略、请求唯一标识和版本兼容性；禁止 `while (true)` 重试、捕获宽泛异常后返回 `null`，或把第三方 JSON 直接透传给前端。
- 写库与外部副作用共存时，明确幂等键、重试边界和补偿方案；在无法确定前次是否成功时，不盲目重试非幂等写操作。
- 事务提交后再执行对外可见的事件、消息或缓存失效。可靠消息复用项目已有机制，不能临时实现“先发消息再写库”。

## 可读性与性能

- 变量和方法名表达业务对象与动作，例如 `syncFundNav()`；禁止 `data`、`obj`、`tmp`、`xxx`、`processData()`、`handle()`、`execute()` 等无业务语义命名。
- 预估集合规模，避免循环中重复序列化、无意义日志、长期持有大对象或无必要地创建对象。百万级数据必须设计分页、分批或流式处理方案。
- 单接口查询超过千级结果、多表 `JOIN`、超过万行文件导入、分钟级定时任务或超过百条的批量接口，评估数据规模、SQL 执行计划、索引、分页/分批方式和资源消耗，并在设计说明中记录结论。
