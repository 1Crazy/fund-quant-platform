# Java 代码评审规范

代码评审先找会影响正确性、安全性、数据一致性和可维护性的事实问题，再讨论风格。不要用偏好替代项目既有约定。

## 优先级

- `P0`：数据错误、权限绕过、安全漏洞或数据丢失，必须阻断合入。
- `P1`：事务、并发、SQL 性能或接口兼容问题，应在合入前修复。
- `P2`：可维护性、命名和重复代码，应在当前改动可小范围修复时处理或明确记录。

## 评审顺序

1. 需求与范围：实现是否覆盖需求，是否引入无关重构、依赖升级或假设性兼容代码。
2. 架构与模型：Controller、Service、Mapper 是否越层；Entity 是否泄露；BO/VO、校验和权限边界是否正确。
3. 数据与事务：SQL 是否注入安全、存在 N+1/深分页/无索引风险；迁移、约束、事务与异常回滚是否一致。
4. 行为与性能：状态机、幂等、并发、外部调用超时与失败处理是否完整；是否有 Service 膨胀、重复逻辑和魔法值。
5. 测试与可观测性：是否覆盖关键正常/异常路径，日志和响应是否泄露敏感信息，是否能定位失败原因。

## 输出要求

- 只报告可复现、影响明确的问题；按 `P0`、`P1`、`P2` 排序，并标明文件与单点行号。
- 每项包含：问题、触发条件、影响、建议的最小修复。没有问题时明确说明，并列出未覆盖的验证风险。
- 不把命名偏好、纯格式或无证据的未来风险列为缺陷；这类内容最多作为可选建议，且不能掩盖真实问题。
