# 幂等、并发、任务与日志

涉及导入、同步、审批、批量操作、定时任务、状态变更、金额或数量时，先识别重复提交、并发写入和故障重试风险。前端禁用按钮不能作为正确性保障。

## 跨资源一致性

- 同时涉及数据库、Redis、MQ、外部 HTTP 或文件时，明确主数据、成功标准、失败路径和一致性策略；不能假定一个本地事务会自动覆盖外部副作用。
- 禁止在数据库事务中调用慢 HTTP、MQ、文件或其他外部服务，例如 `@Transactional` 方法内 `save()` 后直接 `callRemote()`。
- 优先使用本地事务加状态记录/Outbox、事务提交后异步处理、明确补偿和可控重试；重试必须有幂等键、上限和告警，避免无限重试或重复副作用。

## 幂等与并发

- 创建、导入、同步、审批、支付、批量操作和定时任务必须评估幂等：重复请求或重试不能重复创建数据、重复扣减或重复推进状态。可按业务选择防重复 token、幂等 key、唯一约束和状态判断，前端禁用按钮不能作为唯一保障。
- 业务幂等键优先于临时技巧；明确其生成方、作用范围、存储位置、有效期和重复请求的语义（返回已有结果或明确重复错误）。禁止仅用时间戳或随机数作为唯一幂等保障。
- 并发控制优先顺序为：数据库唯一约束 > 带前置条件的条件更新 > 乐观锁 > 状态机 > 分布式锁。根据业务选择能覆盖实际竞争窗口的机制，禁止默认用分布式锁解决所有并发问题；仅在跨资源竞争且数据库无法表达时考虑项目已有分布式锁。
- 涉及状态、金额、数量或审批的更新，禁止“先普通查询、后无条件修改”。使用带版本号/前置状态的条件更新、锁或数据库约束，并检查受影响行数。
- 并发控制不能只依赖 JVM 内存锁或前端限制；多实例部署下必须使用可跨实例生效的数据库或项目基础设施能力。
- 涉及资金、行情或同步结果时，额外评估事务隔离级别、并发覆盖、重复数据和数据时间窗口；禁止默认假定“查询后更新”一定安全。

## 状态流转

- 订单、审批、任务和同步状态的转换集中在 `approve()`、`cancel()`、`complete()` 等具有业务语义的 Service 方法或状态机能力中；不要在任意分支散落 `entity.setStatus(...)`。
- 每次转换明确当前状态、目标状态、触发动作和失败语义，并使用前置状态条件更新或等效并发控制。不要在新模块中为了这一规则强制改造成富领域实体；沿用模块既有分层即可。
- 简单 CRUD 的状态字段更新可留在 Service，但仍要校验前置状态、权限和受影响行数；复杂流程必须通过明确的状态转换方法或状态机集中管理。

## 定时任务

- 定时任务必须可安全重复执行，记录任务标识、范围、开始/结束时间、耗时、成功/失败数量和异常原因。
- 禁止单次任务无分页地处理大量数据。大任务按主键、时间或固定批次分页处理，并在每批次控制事务范围与失败恢复策略。
- 任务异常不得静默吞掉；明确重试、告警和人工补偿边界，避免失败后无限重跑。
- 通用批处理同样采用分批读取与写入，控制 `batch size`、超时、内存、重试和 checkpoint；禁止 `selectAll()` 后一次性将全部实体留在内存中。

## 缓存一致性

- 新增缓存前说明 key 设计、过期时间、读取/更新策略和删除策略；缓存内容、命名空间和租户边界必须可追溯。
- 禁止永久缓存业务数据，禁止把 Redis 当主数据库。写操作后评估缓存失效、更新顺序和并发一致性，优先复用项目已有缓存封装。

## 结构化日志

- 日志包含定位问题所需的业务 ID、关键受控参数、动作、结果和耗时；避免无上下文的“开始处理”“执行失败”。
- 异常日志包含业务上下文和异常对象，例如 `log.error("同步失败 fundCode={}", fundCode, e)`，而不是只记录 `e`。
- 不记录密码、令牌、证件号、完整请求体、完整第三方响应或其他敏感数据。对高频循环和大批任务控制日志级别与采样，避免日志本身造成性能问题。
